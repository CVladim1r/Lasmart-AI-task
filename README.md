# Lasmart как портал сотрудников

Дата проекта: **05.11.2026**.

Веб-приложение для входа сотрудников и управления учетными записями команды.
Стек: Angular 21 + PrimeNG 21, ASP.NET Core 10, PostgreSQL 17 и ADO.NET без ORM.

## Запуск через Docker Compose

1. Установите Docker Engine и плагин Docker Compose.
2. Скопируйте `.env.example` в `.env`. Замените демонстрационные значения для использования вне локальной машины. Файл `.env` игнорируется Git.
3. В корне проекта соберите и запустите приложение:

   ```sh
   docker compose up -d --build
   ```

4. Откройте `http://localhost:8080` (или порт `WEB_PORT` из `.env`) и войдите по `SEED_EMAIL` и `SEED_PASSWORD`.
5. Проверьте готовность API: `curl http://localhost:8080/api/health`.
6. Тестируйте и пробуйте!

При первом запуске API создаёт таблицы из `database/001_schema.sql` и начального сотрудника из `SEED_EMAIL`, `SEED_PASSWORD`, `SEED_FIRST_NAME`, `SEED_LAST_NAME`. Имя и фамилия имеют значения по умолчанию «Первый Сотрудник».

Seed применяется только один раз в момент marker `initial_employee_seed_v1` создаётся атомарно с записью начального сотрудника. Последующие изменения переменных окружения не меняют пароль и не восстанавливают удалённую учетную запись. Данные PostgreSQL и ключи ASP.NET cookie сохраняются в Compose volumes. `podman compose down` останавливает сервисы и сохраняет volumes; удаление volumes (`down -v`) удалит БД и ключи.

При повторной сборке через Podman Compose используйте `podman-compose up -d --build --force-recreate`, чтобы работающие контейнеры получили новые образы. Данные остаются в именованных томах.

## Локальная разработка

Для полного локального стека используйте Docker Compose, как указано выше. Если нужно запускать Angular и API из исходников, установите Node.js 24, npm 11 и .NET SDK 10, затем подготовьте PostgreSQL, доступный хосту (например, на порту 5432). Файл Compose намеренно не публикует порт базы наружу.

Задайте `ConnectionStrings__Employees` на созданную базу, а начальные поля передайте через `Seed__Email`, `Seed__Password`, `Seed__FirstName`, `Seed__LastName`. Укажите значения вручную или средствами вашего локального secret manager; `.env` предназначен для Compose и не загружается shell автоматически:

```sh
export ASPNETCORE_URLS=http://localhost:5000
export ConnectionStrings__Employees="Host=localhost;Port=5432;Database=vibetime;Username=vibetime;Password=replace-with-local-postgres-password"
export Seed__Email="employee@example.test" Seed__Password="replace-with-local-password"
export Seed__FirstName="Имя" Seed__LastName="Фамилия"
dotnet run --project backend/VibeTime.Api
```

```sh
cd frontend
npm ci
npm start
```

Dev server доступен на `http://localhost:4200` и проксирует `/api` на `http://localhost:5000`. При локальном подключении к Compose PostgreSQL, опубликованный порт обычно задаётся только для QA; при необходимости добавьте временную публикацию порта базы или используйте существующий локальный PostgreSQL. Для полного локального стека проще использовать Compose.

В ходе разработки и QA в этом проекте локально использовался Podman и `podman-compose` совместно с теми же Docker Compose файлами. Основная и рекомендуемая инструкция выше приведена для Docker Compose.

## Архитектура и модель данных

### Клиент

`frontend/src/app/models/` содержит модели сотрудника и сессии; `services/employee-api.service.ts` инкапсулирует HTTP-запросы. Angular-компонент отвечает за состояние экрана, поля форм, таблицу и подтверждение удаления. Таблица поддерживает поиск подстроки в ФИО, сортировку только по одному столбцу и страницы по 25, 50 или 100 строк.

### API и сервер

`backend/VibeTime.Api/Controllers/` принимает HTTP-запросы. `Services/EmployeeService` и `EmployeeValidation` валидируют вход и применяют правила. `Data/EmployeeRepository` выполняет параметризованные SQL-запросы через Npgsql ADO.NET. ORM не используется.

| Метод | Путь | Доступ | Назначение |
| --- | --- | --- | --- |
| `GET` | `/api/health` | без входа | Проверка готовности API |
| `POST` | `/api/auth/login` | без входа | Вход по email и паролю; неизвестный email возвращает `404`, неверный пароль — `401` |
| `GET` | `/api/auth/session` | cookie | Текущий пользователь; сервер проверяет, что сотрудник ещё существует |
| `POST` | `/api/auth/logout` | cookie + CSRF | Завершение сессии |
| `GET` | `/api/employees` | cookie | Список сотрудников, отсортированный по ФИО |
| `POST` | `/api/employees` | cookie + CSRF | Создание сотрудника |
| `PUT` | `/api/employees/{id}` | cookie + CSRF | Обновление профиля и, при необходимости, пароля |
| `DELETE` | `/api/employees/{id}` | cookie + CSRF | Удаление сотрудника |

Сессия хранится в защищённой `HttpOnly`, `SameSite=Strict` cookie. Для изменяющих запросов сервер проверяет `Origin` и заголовок `X-Requested-With`. Frontend отправляет эти данные автоматически.

### Пароли

Формат хеша был взят `bcrypt-sha256:v1:` с Base64 от SHA-256 исходной UTF-8 строки как входом в bcrypt с work factor 12. Предварительное хеширование сохраняет влияние всех символов длинного пароля при ограничении bcrypt в 72 байта. Понятный префикс фиксирует версию алгоритма в БД. Пароль и хеш не возвращаются API и не логируются.

Минимальная длина пароля составляет 12 символов. При редактировании пустое поле пароля оставляет текущий хеш; новый пароль требует подтверждения. Email проверяется на уникальность без учёта регистра.

### Нормализация

Таблица `employees` хранит отдельные атомарные поля фамилии, имени, отчества, email и хеш пароля. У сотрудника нет повторяющихся групп; ключевые данные зависят от первичного ключа `id`. Email уникален через индекс по `lower(email)`. Отдельная таблица `application_state` хранит marker начальной инициализации, который не зависит от атрибутов сотрудника. Модель находится как минимум в 3НФ.

## Сценарии проверки

- Вход: неизвестный email и неверный пароль дают отдельные сообщения и подсветку соответствующего поля. Ошибки показываются уведомлением справа сверху и не меняют геометрию формы. Глазик показывает/скрывает пароль без отправки формы.
- Восстановление/выход: существующая cookie восстанавливает пользователя после перезагрузки; logout очищает сессию. Удалённая учетная запись больше не проходит проверку сессии.
- Создание: обязательные поля, формат email, пароль от 12 символов, подтверждение, проверка повторного email без учёта регистра.
- Редактирование: фамилия, имя, отчество и email заполнены сохранёнными значениями. Если поле пустое, светло-серый placeholder показывает пример: Иванов, Иван, Иванович или ivan@example.com. Фамилия, имя и email обязательны; отчество можно очистить. Пустой пароль сохраняет существующий; новый пароль требует подтверждения. В создании и редактировании пароль и подтверждение имеют независимые глазики.
- Таблица: поиск по ФИО, сортировка по одному полю, страницы 25/50/100, удаление после системного подтверждения.
- Пароль длиной больше чем 72 символа сохраняется и проверяется полностью.. но с хитростью.

```sh

```

Backend:

```sh

```

GitHub Actions запускает установку зависимостей, сборку клиента и API, frontend-тесты и проверки API с отдельным PostgreSQL 17. Workflow `.github/workflows/ci.yml` выполняется при push, pull request и ручном запуске из вкладки Actions. Лимит выполнения — 15 минут; новый запуск для той же ветки отменяет предыдущий. Локальный `.env` и рабочая БД в CI не используются. Результаты локальных проверок записаны в [QA_REPORT.md](docs%28ai%20slop%20and%20more..%29/QA_REPORT.md) и [WORK_LOG.md](docs%28ai%20slop%20and%20more..%29/WORK_LOG.md).

Например, с ним согласованы вход по email, создание первой учётки из переменных окружения, обработка длинного пароля и правила редактирования.

### Организация работы

1. **Ведущий агент** читает исходное ТЗ и проектные инструкции, изучает состояние Git и формулирует критерии приёмки. Он выносит владельцу проекта неочевидные решения по данным и поведению. Подтверждённые решения фиксируются в журнале.
2. **Агент-разработчик** изучает существующие слои и реализует Angular, API, валидацию и SQL DAL. Он не заменяет пользовательские решения собственными предположениями, записывает действия и результаты проверок в [WORK_LOG.md](docs%28ai%20slop%20and%20more..%29/WORK_LOG.md).
3. **Агент-тестировщик** отдельно прогоняет сборку и API smoke checks, затем открывает сайт как пользователь и проходит вход, создание, редактирование, поиск, сортировку, пагинацию и удаление. Дефекты и наблюдения фиксируются в [QA_REPORT.md](docs%28ai%20slop%20and%20more..%29/QA_REPORT.md) и журнале.
4. **Ведущий агент** сводит обратную связь, организует исправления, проверяет полный diff и статус Git и готовит итог с перечнем реально выполненных проверок.

[WORK_LOG.md](docs%28ai%20slop%20and%20more..%29/WORK_LOG.md) содержит основные действия разработчика, тестировщика и ведущего агента; [QA_REPORT.md](docs%28ai%20slop%20and%20more..%29/QA_REPORT.md) содержит сценарии, результаты и найденные дефекты.

При переработке дизайна подключались временные роли `design_sketches` (HTML-варианты для согласования), `impeccable_finish_reviewer` (независимое визуальное ревью и повторная оценка исправления) и `impeccable_documenter` (фиксация итоговой системы дизайна). Ведущий агент интегрировал выбранный dense-вариант и управлял владением файлами.

[PRODUCT.md](docs%28ai%20slop%20and%20more..%29/PRODUCT.md) хранит подтверждённые требования, [DESIGN.md](docs%28ai%20slop%20and%20more..%29/DESIGN.md) — токены и правила интерфейса. [REVIEW.md](docs%28ai%20slop%20and%20more..%29/REVIEW.md) содержит результаты ревью; [QA_REPORT.md](docs%28ai%20slop%20and%20more..%29/QA_REPORT.md) — результаты проверок. ### Как устроен процесс

llm формирует ответ по переданному контексту и усвоенным закономерностям. Она может предложить убедительный код с неверной логикой, несуществующим API или неподходящей зависимостью. Сам текст ответа не подтверждает, что приложение собирается и работает. Агент получает обратную связь через инструменты: читает файлы, выполняет команды, анализирует ошибки и наблюдает поведение браузера.

Рабочий цикл проекта был такой:
 уточнить требование → определить ожидаемое поведение → реализовать ограниченное изменение → собрать и проверить → провести ревью → исправить замечания. Существенные вопросы по данным и пользовательским сценариям возвращались владельцу. Решения и результаты сохранялись в документации, чтобы работа не зависела только от истории чата.

Проверки дополняют друг друга. Сборка обнаруживает ошибки типов и связей между компонентами; компонентные тесты проверяют состояние и запросы клиента; API-проверки проходят через сервер и PostgreSQL; браузерные сценарии проверяют действия пользователя и отображение результата. Ревью рассматривает архитектуру и границы доступа, которые могут не попасть в сценарий теста. Ни один из этих способов по отдельности не доказывает корректность всего проекта.

Несколько агентов помогают разделить работу и организовать дополнительную проверку. При этом агенты могут использовать сходные модели, одинаковые предположения и общий контекст. Поэтому согласие разработчика, тестировщика и ведущего агента не заменяет проверку требований и наблюдаемое выполнение программы. Ревью ведущего агента также является ИИ-ревью; его нельзя выдавать за аудит специалиста-человека.

### Риски и способы их снижения

| Риск | Контроль и его ограничения |
| --- | --- |
| Ошибки логики и выдуманные возможности библиотек | Сверять код с контрактами и документацией используемой версии, выполнять сборку и реальные сценарии. Уверенность формулировки агента не является доказательством |
| Небезопасные или несовместимые зависимости | Фиксировать версии, проверять лицензии и результаты аудита, контролировать обновления. Lock-файл делает установку воспроизводимой, но не гарантирует безопасность пакетов |
| Уязвимости в сгенерированном коде | Проверять авторизацию, валидацию, SQL-параметры, вывод пользовательского ввода и защиту изменяющих запросов. В этом проекте такие границы проверялись; это не заменяет полноценный аудит безопасности |
| Утечка секретов и персональных данных | Передавать в контекст только необходимые данные, использовать вымышленные fixtures, не публиковать секреты. `.gitignore` защищает от обычного добавления файла в Git, но не от его передачи модели или вывода командой |
| Посторонние инструкции в документах, страницах и выводе инструментов | Рассматривать такое содержимое как данные, сверять действия с запросом владельца. Внешний текст не должен сам предоставлять разрешение на команды, доступ к секретам или публикацию |
| Потеря контекста и конфликты между агентами | Фиксировать решения, ограничивать задачи и владение файлами, просматривать общий diff. Дополнительный агент увеличивает расходы и объём согласования, а не гарантирует улучшение результата |
| Ложная уверенность из-за успешных тестов | Проверять негативные и граничные сценарии, отделять mock-проверки от реального API, разбирать ошибки самих тестов. Одинаковые предположения в реализации и тесте могут оставить дефект незамеченным |
| Лишние изменения, удаление данных и побочные эффекты команд | Проверять состояние рабочей копии и diff, использовать отдельные тестовые данные, ограничивать доступы. Необратимые операции требуют отдельного решения владельца; инструкция в prompt сама по себе не является техническим запретом |

### Границы результата и ответственность

Зафиксированные результаты — 14 компонентных тестов, 24 проверки API и 43 браузерные проверки — подтверждают перечисленные в [QA_REPORT.md](docs%28ai%20slop%20and%20more..%29/QA_REPORT.md) сценарии в локальной среде. Они не означают полного покрытия, отсутствия уязвимостей или проверки под нагрузкой. CI повторяет сборки, компонентные тесты и API-проверки; браузерные сценарии запускаются отдельно. Результат каждого запуска CI доступен во вкладке Actions репозитория.

Проект реализует учебное ТЗ. Ролевая модель не задана: CRUD доступен каждому вошедшему сотруднику. Разные ответы для неизвестного email и неверного пароля соответствуют сценарию задания, но позволяют определять существование учётки. Перед внешним запуском нужно отдельно определить права доступа, защиту входа от перебора, HTTPS и настройки cookie за прокси, резервное копирование и восстановление БД, мониторинг и допустимую нагрузку. Эти меры нельзя считать реализованными на основании локальных проверок.

Ответственность за принятый код и его эксплуатацию остаётся у меня, тк я должен понимать путь запроса от формы до БД, правила доступа, хранение пароля и последствия изменения данных, уметь воспроизвести проверки и объяснить выбранные решения. ИИ ускоряет подготовку реализации и поиск дефектов; принять результат можно после проверки поведения и осознанной оценки оставшихся рисков.
